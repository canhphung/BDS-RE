StringByteInput vtable is at 0x31d51f0, primary address point 0x31d5200; slot at 0x31d5218 contains 0x1968ce0 (BytesDataInput::readLongString). That function obtains a length through slot +0x40 at 0x1968d05; StringByteInput slot address 0x31d5240 contains 0x187b530 (BytesDataInput::readInt), which reads four raw bytes at 0x187b564 and returns the native little-endian int. readLongString then obtains that many bytes at 0x1968d94. The second string constructs WebToken at 0x18f2b9a; the first and token enter the ConnectionRequest constructor at 0x18f2bab.

The independent decoder therefore consumes a 4-byte big-endian protocol, unsigned-varint-length outer body, then two little-endian 32-bit-length strings. It receives a decoded packet body only: Bedrock packet header, batch compression and RakNet transport are outside its API. Length caps, strict consumption, rejection of noncanonical varints and empty strings are intentional validation policies. The synthetic fixture generated with Python struct is not a client capture. Token strings are returned as UnverifiedLoginBody, never identity or permission claims.

No JWT signature/chain trust, expiry, client proof, online/offline identity policy, encryption negotiation or authenticated session creation is implemented. The decoder is not attached to UDP application traffic yet. A bounded RakNet 9 connection/reliability foundation is now implemented, but application batching and the trusted authentication/session pipeline are still missing. Existing ConnectionRequest::verify and verifySelfSigned symbols have been located but not reconstructed. Real login still requires these stages and a compatible client test.

## Authentication (reconstructed and implemented)

Structured addresses: `reverse/evidence/network_constants.json` → `login_authentication`. VERIFIED_BINARY unless marked.

- **Token check — WebToken::verify (0x19dca50).** Reads the JWT header `x5u` and `alg`; the token is accepted only if `x5u` is one of the supplied trusted keys, the algorithm is known (table strings RS256…ES512 at 0x242b5b4–0x242b5d2), and KeyManager::verify (0x19e57e0) accepts the signature after WebToken::signatureToDER converts the raw r||s form to DER.
- **Chain — UnverifiedCertificate::verify (0x19e41d0).** For each token, the token is first checked against the trusted list; the parent is verified recursively; if the token failed and the verified parent is a certificate authority (`certificateAuthority`, asBool), the check is retried with the parent's `identityPublicKey` appended. A token that passes becomes a Certificate owning its verified parent. The leaf is the last chain entry.
- **Request — ConnectionRequest::verify (0x18f4030).** Verifies the chain, then the client-data token against the leaf's `identityPublicKey`, then Certificate::validate (0x19e4f40) at the server's epoch time: parent valid, `0 < nbf ≤ now`, `0 < exp`, `now ≤ exp`, `nbf ≤ exp` (missing fields read as 0 and fail).
- **Self-signed — ConnectionRequest::verifySelfSigned (0x18f42a0).** Trusts the leaf's own `identityPublicKey` and validates at the leaf's own `nbf`, i.e. without the server clock. It does not re-check the client-data token.
- **Handler (0x18280a0–0x1828371).** Calls verify with the trusted keys (the Mojang root key literal is at 0x242b423); on failure, if the handler flag at +0xc0 is clear — INFERRED to be online-mode — it tries verifySelfSigned; otherwise, or if that fails, it calls disconnectClient("disconnectionScreen.notAuthenticated"). Version mismatches send PlayStatus and then disconnectClient("disconnectionScreen.outdatedClient"/"outdatedServer"). disconnectClient (0x1825660) sends DisconnectPacket(message, false), so the client shows its localised text.

The independent implementation (`src/network/auth.cpp`, Mbed TLS for ES384) follows this algorithm with these deliberate policies: only ES384 is accepted; chains are limited to 8 tokens and tokens to 64 KiB; base64/base64url decoding is strict; the self-signed path also requires the client-data token to verify against the leaf key; the XUID is reported only for chains anchored in a trusted key. Tests use throwaway keys signed by an independent implementation (Python `cryptography`); no genuine Xbox Live chain or real-client capture has been verified. After successful authentication the server currently sends a Disconnect explaining that the encryption handshake (ServerToClientHandshake with `salt`/`signedToken`, strings at 0x182907b/0x1829116) is not implemented.
